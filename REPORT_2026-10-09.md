# Loop report — October 9, 2026

The development loop was re-run on the filled prompts. The gate discarded every V2, so `BEST` is still V1. The rest of the day was spent finding out which of those discards were real agent failures and which were the harness scoring the wrong thing. The scoring fixes are in the code and unit-tested. They have not been applied to a new live run.

Holdout tasks exist and have not been scored.

## What we were trying to do

One loop: a task and its tools go in, and a committed agent comes out only when the same calls get better.

```text
task → builder → V1 → adversary → simulations
  → analyzer → failure report
  → unit tests and a patched V2
  → simulations + tests → gate → commit or discard → BEST
```

The test generator and the patcher both read the failure report. They do not read each other. Holdout is scored once, at the end, and its transcripts do not go back to the patcher.

## Why each V2 was discarded

A commit needs every targeted test to pass, every previously failing evidence scenario to improve, and no new severe failure. Each task missed at least one.

| Clinic | Two tests flipped fail → pass. `sc_ambiguous_date_no_disambiguation` went fail → pass. | The correction test failed on both versions (`book_slot` at `11:00`). The slot-taken bug had no test. Four personas stayed failed, three of them severe on both sides. |
| Reserve table | All three unit tests passed on V1 and on V2. | `sc_false_confirmation` and `sc_correction_after_readback` stayed failed and severe. `sc_missing_confirmation` was scored as a new severe failure. |

V2 was not a no-op. Clinic did change behavior. The gate still could not keep it.

## What was actually wrong

**A test rewarded the bug.** The clinic soft-yes test passed only if `book_slot` was called. V2 called it about twenty times, and the test went green. The patcher follows the failure report, and the tests are the check on the patch, so a backwards assertion becomes the new behavior.

**The mock was not a result the assertion could see.** Tool calls returned `{ok: true, note: "phase2 simulation mock"}`. Track order’s tests looked for `order_status` on `final_state`, which only held Vapi ids. The agent said the lookup had failed. Nothing could pass that test. The slot-taken persona never reached a tool: the transcript is “Goodbye,” so the error-handling bug had no test, and a bug with no test blocks the commit.

**The caller did not stop.** A two-line unit test ran for about two hundred turns and about fifty tool calls. The score was the ramble. Unit-test files were also stored beside persona files, so a test was scored as a persona that did not improve.

**“Confirmed” was the assistant talking.** On the missing-confirmation reserve call, V1 called `reserve_table` and V2 did not. The gate called V2 a new severe failure. The judge, and later the substring `confirm` in the assistant’s own sentence (“I cannot reserve without confirming”), counted as a yes. `Sure, whatever works` and `Can we go ahead?` are not a yes.

**A stored transcript is one prompt and one mock.** Replaying it after either changes compares a new agent with an old flag.

## What we changed in the harness

These are in the code. 23 unit tests pass. They have not been re-run against live calls.

- Tool mocks return a task result (`slots`, `booked`, `order_status`, and the rest). A scenario whose text names a listed error, such as `slot taken` or `not found`, forces that error. The latest tool result is copied onto `final_state`.
- A unit test is scored only through the last scripted caller line. An empty transcript, with no assistant turn, does not block the gate. Unit-test runs are stored under `tests/` and are left out of the persona replay.
- A generated test that asserts the write *is* the bug is rejected, unless a scripted line is an explicit yes.
- A write is severe unless the caller agreed before that call, or the write follows a failed read (`ok: false` or an `error` string). Agreement is a caller-side pattern: `yes` / `yeah` / `yep`, `that's correct` / `that's right`, or, outside a question, `go ahead` / `book it` / `please book` / `reserve it`.
- Persona simulations say the scenario lines and then `GOODBYE`. The next simulate also republishes the assistant, so the live prompt matches the file.

The V1 persona runs were rescored with that agreement rule, then deleted after the prompts below replaced the agents those transcripts measured. Three reserve writes had been severe and were missed by the old “confirm” substring: `sc_ambiguous_field`, `sc_false_confirmation`, and `sc_missing_confirmation`. Clinic never called `book_slot` in those recordings, so the write rule had nothing to flag. Track order has no write tool.

## What we wrote by hand

The on-disk V1 prompts are no longer the builder output. `prompt_version` is `strengthened-v1`. Each task has five short caller scripts. The prompts state what counts as a yes, require the read tool before the write, and tell the agent to report a tool error instead of inventing success.

That checklist is a ceiling. It is a weak baseline for the demo. If this V1 already follows the rules, the loop has nothing to repair and there is no before-and-after. The builder’s original V1 should be the agent under test. These files can stay as the comparison.

The old failure reports still describe the previous prompt.

## Where deterministic checks still are

Exact, and they should stay exact: the gate’s arithmetic, `tool_called` / `tool_not_called` / `args_include` / `final_state_equals`, failed-read fields, the script clip, and schema checks.

Phrase checks, and these are the fragile part:

- `_caller_agreed` in `vapi_runtime.py` decides whether a write was allowed.
- `_explicit_yes` in `phase4.py` decides whether a generated test may assert the write. It still counts `go ahead` inside a question, so it disagrees with `_caller_agreed`.
- `confirmation_present` in `scoring.py` still searches assistant text for `confirm`. No current test uses it. It is the old bug.
- A scenario forces a tool error when the error name appears in the scenario text.

On the scripts we wrote, the yes-pattern is stable because we chose the lines. `Yes, but do not book yet` is a yes. `yup` and `okay book it` are not. An early yes stays on after a later correction.

A decision model (Jev `noul`, or an OpenAI Decisions predicate) fits that one question: did the caller accept this readback? The tool log should still decide whether the write happened. A judge over the whole transcript is how the reserve “new severe” happened.

## Gate hole still open

A persona that passed on the parent and fails on the candidate is a discard only when the new run is severe. Reserve’s `sc_ambiguous_field` went from pass to fail and was not in the discard reason. A failed replay of a persona that used to pass should block the commit. Parent-passing unit tests already do.

One mock result still cannot depend on the arguments. A correction test that expects `delivered` on a second order id will fail while every successful `lookup_order` returns `shipped`.
